# WG-P — Deployment, Chat Connector, CI and Secrets Boundaries (CONTRACT/DEPLOYMENT/1)

## Ownership and trust

This is a cleanroom *deployment* subsystem. It neither runs a gateway nor opens a SQLite connection. It accepts a server-minted `VerifiedIdentity`, not user/chat input masquerading as one, and never issues launch credentials. Only the integration composition root imports `build_component`. The service's trusted network gateway, admission, one-use launch credential lifecycle, state journaling, source publication and merge authorization belong to other WGs.

Module: `nomad_studio.deployment.api.build_component(deps: Mapping[str, object]) -> Component`. There are no module migrations or mutable deployment database tables. WG-P's operations are read-only observations or an explicitly blocked rollback preflight, so no unaudited production state transition is produced. No domain events are emitted; a future actual deployment action must use trusted gateway and StateStore durable event coordination.

| Operation | Envelope | Permission | Payload schema (closed) | Result |
| --- | --- | --- | --- | --- |
| `deployment.status` | `NOMAD/QUERY/1` | `deployment:read` or `deployment:operator` | `{}` | `NOT_RUN/NOT_CONFIGURED` when missing; else `UNKNOWN/EXTERNAL_VERIFICATION_REQUIRED`. Never PASS. |
| `deployment.config_check` | query | read/operator | `{}` | Redacted host status/check codes, `BLOCKED` on health failure; `NOT_RUN` when unobserved; else `UNKNOWN`. |
| `deployment.connector_probe` | query | read/operator | `{}` | `NOT_RUN` without supported bridge or for SIMULATED; `BLOCKED` bad capability/reply; `UNKNOWN` if injected port reports handshake (requires external proof). |
| `deployment.rollback` | `NOMAD/CMD/1` | `deployment:operator` | `{"mode":"preflight","current_release":"<simple-ref>","target_release":"<simple-ref>","backup_verified":true,"owner_approved":true}` | Returns `BLOCKED/NOT_SUPPORTED` even when prereqs set. Host rollback is operator controlled after a separate real authorization, backup verification and database compatibility review. |

Unsupported operations return `DENIED/NOT_SUPPORTED`. Incorrect domains/IDs, wrong protocol major, missing idempotency key, unknown payload fields or invalid types are denied with `MALFORMED_REQUEST`/`INVALID_SCHEMA`. Identity rejected on empty trusted issuer fields, invalid scopes/epochs or expiration. `actor_claim`, `worker_id` and `shift_id` are never used to authorize. All responses avoid returning credential paths and contents. Outcomes use frozen `Outcome(state, code, payload)` values.

### Composition ports

`deps['config']` is a mapping passed to `DeploymentConfig.from_mapping`. See `infra/greenfield/config.example.json`; config keys are closed. Secrets are **file paths only**, never values. `connector_probe_port` is an optional trusted injectable object implementing `capabilities() -> Mapping` and `roundtrip(challenge: str) -> Mapping`. Capability names must report boolean `tool_invocation`, `authenticated_gateway`, `https`; the returned receipt must bind the 256-bit random challenge and version `NOMAD/RECEIPT/1`. Results still return `UNKNOWN` pending a separately witnessed actual ordinary ChatGPT session. `SIMULATED` always returns `NOT_RUN` even with the matching fake.

Inject `dns_lookup` (compatible with `socket.getaddrinfo`), `service_alive` (`() -> bool`), and `now_us` (`() -> int`) for test/host integration. Without a host monitor port, service checks emit `NOT_RUN/NO_HOST_MONITOR`. There are no provider calls inside SQLite transactions.

## Trust/network route: conditional, not deployed

1. Owner selects a reachable **public DNS FQDN** and obtains an HTTPS server certificate and independently administered connector-client CA. Configure a reverse proxy with `infra/greenfield/nginx/nomad-studio-mtls.conf.template` (mutual TLS required; non-TLS denied). A private gateway binds only `127.0.0.1:8765`, never `0.0.0.0`. Apply firewall policies that reject inbound direct gateway TCP; require gateway-side authenticated transport/launch policy even for loopback clients. Client cert verification at proxy does not alone authorize a Studio operation.
2. Owner configures a supported authenticated tool/connector bridge able to perform remote HTTPS/mTLS requests and preserve a verified server authentication context. Ordinary ChatGPT web cannot access a developer's localhost by virtue of being a chat. The connector implementation, identity support and tool schema must be demonstrated; if mTLS is unsupported, select a separately audited authenticated front door with equivalent trusted gateway security and have integrator adjust the operator-owned deployment config. **No unsecured fallback.**
3. Trusted WG-B gateway checks real transport credential, issuer, launch ticket/short-lived capabilities and request scope/epoch; WG-A persists effects. User-pasted worker IDs are public routing data only. Limited launch capabilities are one-use short-lived, held server-side as verifier digests, not standing admin tokens in prompts. Operator holds issuance key and separately authenticates.
4. Actual web-chat acceptance is a manual, authenticated roundtrip *using the chosen supported connector*, with gateway event/receipt readback, a denied unauthorized replay, a 2-job single-response and STOP control check. Run through WG-Q release harness bound to exact source SHA. A local scripted TLS request and any WG-P `connector_probe_port` fake cannot satisfy this gate.

Connector `NOT_CONFIGURED` is the default. `SUPPORTED_TOOL_BRIDGE` requests probe but never upgrades release readiness. `SIMULATED` allows deterministic tests and is strictly non-release. No claim of per-chat identity attestation, High UI setting, 500 actual simultaneous web chats, or remote tool availability is made.

## Linux deployment — cold install procedure

Requirements: private Linux server (systemd, Python >=3.11, preferably 3.12), on-host private non-network SQLite storage, POSIX user/group isolation, an authorized HTTPS/mTLS reverse proxy and trusted connector. External dependencies for live operation are WG-A StateStore, WG-B Gateway transport, trusted configured provider bridge, source/Drive credentials and verified DNS/TLS. No active host or credentials were supplied to WG-P.

1. Create service principal `nomad-studio` with no interactive login. Provision `/opt/nomad-studio/releases/<source-sha>/` via separately authenticated immutable release artifact, and `/opt/nomad-studio/current` via atomically switched *operator-controlled* symlink. Do not publish or merge source as part of this workflow. Create `/var/lib/nomad-studio/state` as `0700 nomad-studio:nomad-studio` on a private local disk; create `/etc/nomad-studio/keys` as `0700` accessible to only appropriate service/proxy principals. Set private credential files `0600`, suitable ownership. Public certificate chains may be less restrictive but default to private. Verify no symlinks in credential path and no group/world-readable private keys.
2. On a clean frozen seed, install the Python project with `python3.12 -m venv venv` then `venv/bin/python -m pip install --no-deps .`. This installs the WG-P package and contracts without modifying pyproject. For **integrated** deployment, first merge and test the 19 owned modules and the root `nomad_studio.app` composition entrypoint. The WG-P-only seed intentionally cannot boot the final service.
3. Copy `infra/greenfield/config.example.json` to `/etc/nomad-studio/config.json`, set to private mode, fill real absolute credential file **paths**, verified DNS, TLS CA/client cert/key, GitHub App private key, Drive OAuth/service credentials, launch signing key and connector name. Configure the approved trusted integration root to consume it. Credential values must not be included in configuration JSON. Mount them through the service security context, preferably a host secret manager or systemd credential facility.
4. The operator creates a short-lived launch issuer signing key using system secure randomness via approved key management, stores it outside the repository, rotates independently of GitHub App, Drive and mTLS keys, revokes stale grant epochs through WG-B, and tests replay denial. GitHub App installation must be restricted to approved repos/actions and Drive principal to approved folders/scopes. Workers do not receive those credentials in prompt/issue/ZIP.
5. Configure a reverse proxy TLS server and mTLS client CA; validate real cert chain/expiry and actual connector support. Apply strict network ACL, no inbound port 8765. Forward application Authorization for WG-B verification, while stripping spoofable identity headers. If a proxy-to-gateway connection is not a suitably protected trust boundary, move to Unix-domain sockets with restrictive filesystem permissions in integration. Obtain explicit WG-B security review before opening remote access.
6. Install `infra/greenfield/systemd/nomad-studio.service` and health service/timer; run `systemd-analyze verify` and `nginx -t` with actual config before enabling. The systemd main unit runs `python -m nomad_studio.app` **only after the integration root exists**. Use `systemctl daemon-reload`, then start only with owner approval. Observe `systemctl show ... -p ActiveState -p ExecMainStatus`; systemd restart alone is not evidence of connectivity or healthy SQLite.
7. Run `python infra/greenfield/host_check.py --config /etc/nomad-studio/config.json`, then a trusted local gateway health query, SQLite WAL/FULL/FK/trusted-schema readbacks (WG-A), TLS/mTLS gateway probe, and finally actual ordinary ChatGPT connector test. Emit receipts with exact integrated tree/source SHA. Until then deployment remains `LOCAL_PATCH_ONLY` / `NOT_CONFIGURED`.

This packet includes a hardened systemd service and Nginx *template*, not a container image. Host-specific uid mapping, secrets custodian, DNS, external connector protocol and product/tool permissions are operator decisions.

## Operational response

**Health and outages.** `nomad-studio-health.timer` triggers local filesystem/DNS/host preflight every five minutes; a local restart gate tests the service status callback. `systemd` restarts the coordination process on failure. Observe bounded gateway health, queue/SQLite WAL state, proxy TLS logs, cert expiry, disk/inode pressure, Drive/GitHub rate limits and backup/restore witness; only WG-M can convert observations into trustworthy alerts, and missing telemetry is `NOT_OBSERVED`.

**Backup/restore.** Coordinate WG-A online SQLite snapshot and WG-L compressed off-host archive. Never merely copy a live WAL `*.sqlite3` and claim a consistent backup. Verify archive digest and perform an isolated real restore, `PRAGMA integrity_check`, V1 schema digest, publisher/outbox reconciliation and a witnessed receipt before switching traffic. Never delete archived history by rollback.

**Rollback.** Set maintenance/DRAIN through trusted gateway; stop new claims and reconcile external publication effects. Owner selects an immutable *known-good* release SHA and independent verified database backup. Check the exact pinned Studio V1 schema identity. V1 deployment supports same-schema release rollback only; it does not attempt database conversions or reverse migrations. Take a verified snapshot, use operator-controlled atomic symlink switch and controlled service restart, verify SQL/event/state and provider readbacks. On any mismatch stop/reverse traffic; rollback must not auto-merge, delete archives or authorize code changes. WG-P `deployment.rollback` only checks inputs and always blocks host mutation.

**Rotation.** Rotate one service credential at a time: CA trust overlap, mTLS key/cert deploy+test, GitHub App private key replace/permission/scope/readback, Drive refresh token reauthorize/revoke, launch issuer signing key + WG-B epoch/session revoke. Restart with drain and validate all proxies/gates, then revoke old credentials. Do not expose values in logs/status/CI.

**Failure codes / limits.** `INVALID_SCHEMA` (closed config/payload), `INVALID_SCOPE` (no public listener/scope denied), `IDENTITY_UNVERIFIED`, `EXPIRED_GRANT`, `NOT_CONFIGURED`, `NOT_SUPPORTED`, `DNS_FAILURE`, `HOST_CHECK_FAILED`, `INSECURE_PERMISSIONS`, `INSECURE_SYMLINK`, `PROVIDER_UNKNOWN`, `UNTRUSTED_CONNECTOR`, `EXTERNAL_VERIFICATION_REQUIRED`. HTTPS host probe enforces a 10s timeout and <=4096-byte receipt, TLS verification enabled. A Python service process handles no network requests until WG-B integration composes transport. Raw host checks cannot prove client connector identity or external availability.

## CI and evidence

- `.github/workflows/greenfield-wg-p.yml` cold-installs the Python seed, runs frozen contract and WG-P suites, and scans for credential literals/insecure service listeners.
- `.github/workflows/greenfield-integrated.yml` first calls `ci_gate.py`, fails when any of 19 domains or gateway is absent, then executes a nonempty required test suite for every one of the 19 domains, gateway and contracts (including integration/chaos/security workers) and secret scan. No `continue-on-error`, optional skips, or forced green for missing modules.
- `infra/greenfield/security_scan.py` is only a known-token/private-key heuristic. Release process also needs authenticated secret scanning of actual Git history and artifacts.
- `gateway_https_probe.py` can verify selected host TLS/mTLS challenge path after the gateway implements it; it always reports `real_chat_verified:false`. Its route `/v1/connector/probe` and closed receipt schema are an **integration proposal**, not part of frozen gateway contract: WG-B/integrator must align endpoint and method without edits to frozen shared version-1 envelopes. Until then mark real host TLS probe `NOT_RUN`.
- Local tests inject restart/stopped host, lost host monitor, broken DNS, key permissions/symlink and connector timeout/bad challenge. Actual remote host/restart, issued mTLS certs, real ChatGPT tool operation, real GitHub/Drive providers, integrated 500/800 capacity and off-host restore are `NOT_RUN` pending integration.

## Integration changes requested

`INTEGRATION_CHANGE_REQUEST`: WG-B gateway + operator root must agree on HTTPS proxy identity verification and connector challenge path; the probe is not a new frozen operation or permission. WG-O console supplies owner-authenticated launch interface; WG-B owns ticket issue/revoke, and WG-Q binds release acceptance to live actual receipts and final code SHA. WG-A exposes StateStore health/query; WG-M supplies actual monitor callback. Integrator chooses a secure bridge supported by the actual ChatGPT tool environment and provides `connector_probe_port`, never imports other WGs directly into this subsystem.
