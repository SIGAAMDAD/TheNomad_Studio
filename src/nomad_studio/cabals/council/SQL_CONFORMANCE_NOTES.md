# CAB-F — frozen R8 SQL conformance / R9 semantics

Authoritative physical SQL: `CONTRACTS/initial_schema_v1.sql`, immutable at P1.

* `v1_council_cases`: `(feature_id FK v1_feature_runs, case_id PK, bible_pair_digest, state, conflict_digest)`; one case per immutable conflict payload. `state` CAB-F values `OPEN`, `RESOLVED`, `OWNER_ACTION_REQUIRED`. All source inputs and alternatives preserved as content-addressed JSON outside the SQL transaction; SQLite retains their SHA-256.
* `v1_council_proposals`: `(proposal_id PK, case_id FK, author_cabal_id, proposal_digest, compliance_ref, selected 0/1)`; every alternative inserted once. `selected=1` for at most one proposal per case enforced in the CAB-F writer transaction. The schema itself does NOT enforce unique selected-per-case; mandatory negative test covers concurrent resolution. `compliance_ref` is `cas:<sha256>` of verifiable external CAB-D assessment and provenance evidence links, stored for selected or owner-escalated proposals, with immutable evidence preserved.
* `v1_council_dissent`: `(dissent_id PK, case_id FK, author_id, reason_digest)`; append-only even after selected resolution. Immutable CAS records include reason, clause references, targeted proposal, evidence and author. No unbounded updates/deletes.
* `schema_table_owners.json` assigns exactly these **three** tables to CAB-F. The injected P2 `db.write` capability must reject inserts/updates/deletes/DDL to every other table, including `v1_idempotency`, `v1_events`, all bible/owner/QA/source tables. CAB-F reads `v1_projects`, `v1_feature_runs`, `v1_bible_editions`, `v1_cabals`, `v1_memberships`. It never directly mints QA, owner, source or activated-bible receipts.
* **Lineage:** `feature_id` is globally unique and checked against `project_id`, `active_contract_digest`, `bible_pair_digest`, `graph_revision`; project must be ACTIVE. Activated DESIGN/TECHNICAL edition identities rechecked under the transaction. CAB-D's snapshot and clause provenance verification and conflict assessment are injected, required before resolution. A stale bible or graph conflicts, not a speculative approval.
* **Idempotence:** fixed natural `case_id`, `proposal_id`, `dissent_id` plus canonical digest equality; same bytes are harmless retries, changed intent using the same ID conflicts. No CAB-F ownership of root `v1_idempotency`, so no direct insert there. No provider effects inside the SQLite writer transaction.
* **Content**: the frozen SQL only contains digests, not alternatives or dissent text. P2 **must inject a durable immutable CAS `records.put/get` that readbacks exact JSON bytes and binds digest** (prefer CAB-I artifact CAS); an in-memory store is permitted only for labeled unit fixtures, not production. Returning a SQL-only row without persisted CAS cannot meet no-loss/dissent requirements.
* **Authority:** `resolve_case` treats the supplied Decision as untrusted and compares to CAB-D's fresh trusted assessment evidence. Positive resolution is advisory only. Owner/bible amendment goes to CAB-D/owner via `OWNER_ACTION_REQUIRED`; no authoritative source, QA or bible mutation.
* **P2 integration:** replace old `app.py` legacy convergence gateway and `state/schema.py` legacy convergence SQL with new CouncilPort registration and root DB capability injection. This worker is forbidden to touch root glue. A failed port bind is a local P2 gate, not a `UNSUPPORTED` successful runtime.

* **Frozen type import:** `runtime_ports_v1.Decision/Result` is imported directly from the exact `CONTRACTS/runtime_ports_v1.py`. P2 must package that frozen module with the new runtime; no local duplicate or historical aliases. CAB-F unit invocation sets `PYTHONPATH=src:$KIT/CONTRACTS`.
